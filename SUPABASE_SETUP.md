# Supabase

O frontend já possui um repositório de vagas em `src/js/services/vagas-repository.js`. Sem configuração, ele usa `localStorage` para desenvolvimento. Para conectar ao Supabase, preencha `src/js/config/supabase.js` com a URL do projeto e a chave pública `anon`.

Nunca use a chave `service_role` no navegador.

## Contas de candidatos

O login usa o Supabase Auth para validar a senha e a tabela `public."user"` para
os dados do perfil. Crie a tabela e as políticas abaixo no SQL Editor:

```sql
create table if not exists public."user" (
  id_user bigint generated by default as identity primary key,
  nome_user text not null,
  email_user text not null unique,
  senha_hash text not null,
  telefone_user text,
  created_at timestamptz not null default now(),
  data_nascimento date,
  cidade_user text,
  estado_user text
);

alter table public."user"
  add column if not exists senha_hash text;

alter table public."user" enable row level security;

drop policy if exists "Usuários autenticados leem o próprio perfil" on public."user";
create policy "Usuários autenticados leem o próprio perfil"
  on public."user" for select to authenticated
  using (lower(email_user) = lower(auth.jwt() ->> 'email'));

drop policy if exists "Usuários autenticados criam o próprio perfil" on public."user";
create policy "Usuários autenticados criam o próprio perfil"
  on public."user" for insert to authenticated
  with check (lower(email_user) = lower(auth.jwt() ->> 'email'));

create or replace function public.login_user(p_email text, p_senha_hash text)
returns table (
  id_user bigint,
  nome_user text,
  email_user text,
  telefone_user text,
  created_at timestamptz,
  data_nascimento date,
  cidade_user text,
  estado_user text
)
language sql
security definer
set search_path = public
as $$
  select id_user, nome_user, email_user, telefone_user, created_at,
         data_nascimento, cidade_user, estado_user
  from public."user"
  where lower(email_user) = lower(p_email)
    and senha_hash = p_senha_hash
  limit 1;
$$;

revoke all on function public.login_user(text, text) from public;
grant execute on function public.login_user(text, text) to anon, authenticated;

create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
  insert into public."user" (nome_user, email_user, senha_hash)
  values (
    coalesce(new.raw_user_meta_data ->> 'name', new.email),
    lower(new.email),
    new.raw_user_meta_data ->> 'password_hash'
  )
  on conflict (email_user) do update
    set nome_user = excluded.nome_user,
        senha_hash = excluded.senha_hash;
  return new;
end;
$$;

drop trigger if exists on_auth_user_created on auth.users;
create trigger on_auth_user_created
  after insert on auth.users
  for each row execute procedure public.handle_new_user();

-- Preencha senha_hash com o SHA-256 da senha escolhida antes de executar.
insert into public."user" (
  id_user, nome_user, email_user, telefone_user, created_at,
  data_nascimento, cidade_user, estado_user, senha_hash
)
values (
  1, 'Leonardo Lopo  λ', 'leonzz@leonzz.co', '11 99999-9999',
  '2026-10-14 10:53:09.231841+00', '2005-05-05', 'São Paulo', 'São Paulo',
  '<SHA256_DA_SENHA>'
)
on conflict (email_user) do nothing;
```

A senha também deve ser cadastrada no Supabase Auth. Para o e-mail acima, crie o usuário
correspondente em **Authentication > Users** ou pelo cadastro da aplicação e
defina a mesma senha. Depois disso, o login carrega o perfil pelo `email_user`.

## Tabela `vaga`

O frontend usa as colunas abaixo, seguindo a estrutura já existente no projeto:

- `id_vaga`
- `titulo_vaga`
- `descricao_vaga`
- `atividades_vaga`
- `requisitos_vaga`
- `areaAtuacao_vaga`
- `cargaHoraria_vaga`
- `modalidadeContratacao_vaga`
- `beneficios_vaga`
- `statusCand_vaga`
- `img_vaga`
- `created_at`
- `diferenciais_vaga`
- `endereco_vaga`
- `Empresa`

Se a tabela ainda não existir, execute no SQL Editor do Supabase:

```sql
create table public.vaga (
  id_vaga bigint generated by default as identity primary key,
  titulo_vaga text not null,
  descricao_vaga text,
  atividades_vaga text,
  requisitos_vaga text,
  "areaAtuacao_vaga" text,
  "cargaHoraria_vaga" text,
  "modalidadeContratacao_vaga" text,
  beneficios_vaga text,
  "statusCand_vaga" text not null default 'Ativa',
  img_vaga text,
  created_at timestamptz not null default now()
  , diferenciais_vaga text
  , endereco_vaga text
  , "Empresa" text
);

alter table public.vaga enable row level security;

create policy "Vagas ativas podem ser lidas publicamente"
  on public.vaga for select
  using (lower("statusCand_vaga") = 'ativa');
```

Se `public.vaga` já existe, execute pelo menos a parte de RLS abaixo para permitir que a chave pública leia as vagas com status `Ativa`:

```sql
alter table public.vaga enable row level security;

drop policy if exists "Vagas ativas podem ser lidas publicamente" on public.vaga;
create policy "Vagas ativas podem ser lidas publicamente"
  on public.vaga for select
  using (lower("statusCand_vaga") = 'ativa');
```

O repositório converte esses nomes para o modelo usado pelas telas e também aceita o fallback local. As operações de criação, edição e exclusão exigem políticas RLS próprias e autenticação antes de serem liberadas para usuários reais.
